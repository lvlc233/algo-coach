# 排序链表 (Sort List)

LeetCode 148 | 归档: 2026-06-20 | 状态: 已推导（待判题）

## 核心洞察（一句话）

链表可以近似均分，左右半段的排序与原问题同构，两个局部有序结果又能线性合并，因此归并排序能消除朴素方法中的重复比较。

## 追问阶段卡点与突破

1. **朴素思路是利用 `next` 向后寻找更小节点**：第一反应接近选择排序，从当前位置反复扫描后续链表，寻找比自己小的元素。这样会重复遍历后续节点，时间复杂度容易达到 `O(n²)`；交换链表节点还需要同时维护前驱与后继
2. **已有局部能力没有自动组合成整体解法**：已经知道快慢指针可以找中点，也知道如何合并两个有序链表，但没有想到把它们组合为“找中点 → 拆成两半 → 分别排序 → 合并”
3. **意识到可以一直拆到单节点后才理解递归**：单节点链表天然有序，是递归停止条件；从这些最小有序子问题开始，才能逐层向上合并
4. **切断链表是问题真正缩小的必要条件**：找到中点后，必须将中点前一个节点的 `next` 设为空。否则左半仍连接着右半，递归处理的链表没有缩短，可能无限递归或栈溢出
5. **从“存在比较”联想到分治过于宽泛**：存在比较不意味着应该分治；寻找最大值也能分治，但线性扫描已经最优
6. **真正的子问题不是比较两个元素**：子问题是“把一条更短的链表排好序”，与原问题形式相同；比较只是合并阶段的基本操作
7. **分治需要三个结构条件**：问题规模可以稳定缩小、子问题与原问题同构、子问题结果可以高效合并
8. **148 的条件完整**：快慢指针支持近似均分，两半仍是排序链表问题，两个有序链表可以复用 21 的方法线性合并
9. **复杂度改善来自减少重复工作**：朴素方法反复让节点与大量后续节点比较；归并排序先建立局部有序性，使每个节点在每层合并中只参与一次线性选择

## 用户复盘

这道题没有自然想到分治。朴素想法是利用 `next` 的访问方式，从当前位置不断向后寻找更小的元素，但这种方法会反复扫描后续节点，时间复杂度达到 `O(n²)`。

真正的卡点不是不会找中点，也不是不会合并有序链表，而是没有想到把两个已经掌握的操作组合起来。意识到链表可以不断拆开，直到每段只剩一个天然有序的节点后，才理解归并分治的做法。

本轮进一步暴露出一个尚未稳定掌握的问题：什么时候应该使用分治，以及应该把什么识别为原问题的同构小问题。

## 用户重要思考

> 好思路，分治是原问题的“空间结构”减半，但是问题不变，而和动态规划的分子问题有一定的差距。

这个视角抓住了分治常见的形态：按输入结构切开，问题类型不变，只缩小规模。进一步的稳定边界是：分治的子问题通常相对独立，分别求解后合并；动态规划的子问题通常大量重叠，需要保存和复用状态。

## 分治识别链条

```text
链表可找中点
→ 可均衡切成两半
→ 子问题仍是“排序链表”
→ 两个有序结果可线性合并
→ 适合归并分治
```

## 复杂度与递归边界

- 单节点或空链表天然有序，递归在此停止
- 每层合并总共处理 `n` 个节点，近似均分产生 `log n` 层，因此时间复杂度为 `O(n log n)`
- 合并过程只重连原节点；递归调用栈占用 `O(log n)` 空间
- 中点处分链后必须切断左半与右半的连接，确保每次递归的问题规模确实缩小
