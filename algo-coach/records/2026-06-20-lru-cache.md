# LRU 缓存 (LRU Cache)

LeetCode 146 | 归档: 2026-06-20 | 状态: 已推导（待判题）

## 核心洞察（一句话）

LRU 同时要求按 `key` 快速定位节点、按使用时间快速移动和淘汰节点，因此需要哈希表与双向链表组合。

## 追问阶段卡点与突破

1. **最初想到三个结构**：设想分别使用 `map: key -> value`、维护时间顺序的链表，以及 `map: key -> index`。链表没有稳定的数组下标，节点移动后 `index` 难以维护；更自然的结构是 `map: key -> 双向链表节点`，节点本身保存 `key`、`value`、`prev` 和 `next`
2. **链表适合表达使用时间顺序**：将最新使用的节点放在头部，最久未使用的节点自然位于尾部。成功访问或更新节点时将其移动到头部，容量超限时淘汰尾部节点
3. **最初认为单向链表足够**：只考虑了选中节点可以移动到头部，忽略了从链表中间摘除节点时还需要修改前驱节点的 `next`
4. **从单向切换到双向链表**：通过哈希表直接跳到任意中间节点时，手里只有当前节点。双向链表让节点能够同时找到前驱和后继，从而在 `O(1)` 时间内完成摘除和移动
5. **形成双向链表识别信号**：顺着链表路径逐步处理时，当前节点的前驱通常已在手里，单向链表可能足够；随机跳到任意中间节点并要求快速摘除或移动时，需要双向链表提供前驱信息
6. **淘汰需要同步更新两个结构**：从链表尾部摘除最旧节点后，还必须从哈希表删除对应的 `key`，否则 `get(key)` 仍可能找到已淘汰节点
7. **虚拟头尾节点统一边界**：最初不知道为什么需要虚拟节点。加入 `dummyHead` 和 `dummyTail` 后，空链表、单节点、头部插入和尾部删除都能使用统一的连接操作
8. **新节点的方向一度放反**：约定越靠近头部越新时，已有 `A` 后插入 `B` 应为 `H <-> B <-> A <-> T`，而不是 `H <-> A <-> B <-> T`
9. **容量计数只跟真实增删有关**：新增不存在的 `key` 时 `size + 1`，淘汰节点时 `size - 1`；更新已有 `key`、读取节点或移动节点都不改变 `size`

## 完整结构

```text
map: key -> 双向链表节点

dummyHead <-> 最新节点 ... 最旧节点 <-> dummyTail
```

- `get(key)` 命中：返回节点值，并将节点移动到头部
- `get(key)` 未命中：返回 `-1`，链表和哈希表不变
- `put(key, value)` 命中：更新原节点的值，并移动到头部，`size` 不变
- `put(key, value)` 未命中：创建节点、写入哈希表并插入头部
- 新增后超过容量：删除 `dummyTail.prev`，同时从哈希表删除其 `key`

所有哈希查找、节点摘除、头部插入和尾部淘汰操作均为 `O(1)`。

## 用户复盘

这道题是一个复合结构问题，复合的是 `map` 和链表。

链表比较自然，因为题目最大的特点是顺序，而链表很适合表示顺序。最初只想到链表的单向传播性；之后发现，如果通过 `map` 直接访问任意中间节点，单向链表会缺少前驱信息，无法方便地把中间节点摘除并重新连接。

由此理解了双向链表的使用场景：访问位置不只在首尾，并且会随机访问和移动任意中间节点时，需要同时保存前驱和后继。

之后整体结构变得自然：`map` 负责快速定位，双向链表负责维护使用顺序。成功访问或更新节点时移动到头部，超过容量时淘汰尾部节点。

另一个补充点是虚拟头尾节点。它们可以统一链表边界操作；类似技巧在很多单向链表题中也适用，例如增加虚拟头节点来简化删除头节点等特殊情况。
